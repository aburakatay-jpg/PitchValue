# Canonical database foundation

The canonical PostgreSQL schema separates football identity, provider traceability,
match facts, statistics, odds, quality state, and import audit metadata. All primary
keys use PostgreSQL `bigint GENERATED BY DEFAULT AS IDENTITY`. Instant timestamps use
`timestamptz`; date-only validity and season boundaries use `date`.

`country_code` means an ISO 3166-1 alpha-3 country code, such as `GBR`, `FRA`, or
`DEU`. `competitions.jurisdiction_code` separately identifies the football
association or competition jurisdiction, such as `ENG`, `SCO`, or `UEFA`. Both are
needed because one sovereign country can contain multiple football jurisdictions,
while a continental competition may have a jurisdiction but no single country.

## Tables

- `providers` identifies external data, odds, and future source systems.
- `competitions` stores canonical competitions independently of provider naming.
- `competition_provider_refs` maps provider identifiers, names, or codes to a
  canonical competition.
- `seasons` scopes arbitrary historical or future seasons to a competition. The
  composite `(season_id, competition_id)` key lets PostgreSQL enforce that matches
  cannot combine a season with the wrong competition.
- `teams` stores canonical club identities. `normalized_name` is indexed but is not
  unique because normalization collisions must not merge real clubs.
- `team_aliases` records provider-specific and provider-independent name variants.
  A non-null provider team ID requires a provider and is unique within that provider.
- `matches` stores canonical fixture identity, scheduling, score, result, stage, and
  venue facts. It deliberately contains neither odds nor match statistics.
- `match_provider_refs` lets multiple provider records map to one canonical match.
  External match IDs are unique only within their provider.
- `match_statistics` stores nullable canonical match statistics with optional
  provider traceability. PostgreSQL `UNIQUE NULLS NOT DISTINCT` permits only one
  providerless canonical row per match.
- `odds_snapshots` stores one normalized odds observation per row across bookmaker,
  market, selection, line, time, and snapshot type.
- `data_quality` stores per-match availability and verification flags plus an
  optional exact score and optional JSONB flags.
- `import_batches` records future ingestion runs, counters, source identity, status,
  and errors without placing raw source data in canonical tables.

## Reconciliation and NULL policy

Provider references preserve source identity while allowing several source records
to resolve to one canonical team, competition, or match. The match reconciliation
index supports candidate searches by competition, season, teams, and kickoff, but is
intentionally not unique because postponed or rescheduled records may overlap.

Unknown football values remain SQL `NULL`. Statistics have no zero defaults. Only
import counters and boolean state flags have deliberate defaults. Odds and other
decimal values use exact `numeric` columns rather than binary floating point.

`matches.home_score` and `matches.away_score` mean the score after 90 minutes plus
stoppage time. They are not aggregate, extra-time, or penalty-shootout scores.
`result` is the normal-time 1/X/2 outcome derived from those two fields. PostgreSQL
rejects contradictory `FINISHED` score/result combinations. Extra-time and penalty
scores remain in their dedicated fields and do not rewrite the normal-time result.
An `AWARDED` match is administrative and is deliberately excluded from ordinary
played-match score/result comparison; `score_is_awarded` identifies an awarded score
where applicable.

Provider external identifiers remain nullable where the schema permits missing
source identity. When supplied, competition, team, match, and market external IDs
must contain non-whitespace content. A provider market ID also requires a provider;
providerless canonical odds rows remain valid when no provider market ID is stored.

## Delete and audit policy

Foreign keys use restrictive deletion. Canonical competitions, seasons, teams,
matches, providers, and their traceability/audit children cannot be accidentally
removed while referenced. No historical child uses automatic cascading deletion.
`updated_at` receives a creation default and must be changed explicitly by the
future write path; no trigger framework is introduced at this stage.

## Extensibility and deferred identity

The migration seeds only the ten V1 competition identities, idempotently. Later
migrations or importers may add any older or newer seasons; no 2024/25 or 2025/26
match data is seeded here. Stage, market, selection, gender, provider type, season
status, and provider naming remain text-based where vocabularies are expected to
grow. Controlled lifecycle values use database checks and can be extended by a
future migration.

Availability and injury tables are deferred until an approved canonical player
identity model exists. Storing long-lived availability against player names now
would create avoidable reconciliation debt.
